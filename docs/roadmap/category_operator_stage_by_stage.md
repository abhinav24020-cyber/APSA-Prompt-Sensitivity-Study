# Stage-by-Stage Guide for Selecting and Testing a Perturbation Operator

Follow these stages to turn a selected prompt into an auditable result. The final record answers which operator was chosen, how little it changed the input, how much it changed the response, and whether the answer or behavior changed. The existing implementation plan defines the metrics, discovery rankings, validation procedure, and worked output. [Category operator implementation plan](category_operator_implementation_plan.md)

| Stage | Work to perform | Completion check |
|---|---|---|
| **1. Register the prompt** | Accept a dataset prompt ID or original text plus a category. Store the exact original text, category, reference answer or task tests, and prompt ID. Choose a model or fixed panel, input edit budget, and optional minimum desired output change before generating responses. Use 0.10 as the default study budget. If the category or reference is ambiguous, resolve it before scoring. | The same recorded inputs can recreate the run. |
| **2. Load the category recommendation** | Read the ranking for the category and requested budget. Record the top operator and why it suits that category. Label the recommendation exploratory or validated according to its evidence. For a custom budget without a category ranking, treat the category leader as a starting candidate and use the actual budget to filter generated edits. | The recommendation includes its source, budget, and evidence status. |
| **3. Build and audit candidates** | Use the registered APSA operators and fixed candidate seed. Generate one candidate per operator for the main comparison. Save the exact text diff and raw and normalized edit distances. Reject no-ops, over-budget edits, changed tasks, and uncertain preservation. Check protected content such as quantities, premises, labels, quoted text, or code signatures. Log each rejection and generator error. | All included candidates preserve the task and fit the same input budget. If none qualify, return `no_eligible_edit`. |
| **4. Collect matched responses** | For every model, generate one original anchor, two unchanged repeats, and one response per eligible candidate. Keep the same system prompt and decoding settings. Record generation IDs and retry eligible failures with the study’s retry policy. Flag empty, truncated, or missing outputs. | Each scored operator has one treatment and both controls for every model in scope. Incomplete comparisons carry an `incomplete` status. |
| **5. Score output differences** | For each eligible treatment, compute semantic distance to the anchor, subtract the mean distance of the unchanged repeats, and retain negative values. Average across the fixed panel if applicable. Also record character and token distance, normalized answer equality, and correctness before and after. For code, record unit-test outcomes and signature compliance. | Distances, control subtraction, and correctness are traceable to the exact response records. |
| **6. Choose and explain the edit** | Select the largest measured excess distance under the budget. For exact ties prefer fewer character edits, then lower normalized input distance, and retain all ties in the evidence. If a target change was set, also identify the smallest input edit that met it. Otherwise show the trade-off between input edits and measured response change. Explain the choice using actual comparison scores and task-preservation evidence. | The selected edit can be reproduced by applying the recorded rule to the candidate table. An unsuccessful target is labeled `target_not_met`. |
| **7. Publish the prompt result** | Generate the user-facing result in the format shown in Section 7 of the plan. Export the original and modified prompts and responses, candidate and pair IDs, all eligible alternatives and scores, exclusions, model scope, and evidence status. Distinguish a category recommendation, a measured prompt result, and a single observed model case. | A reader can reconstruct the selection and tell whether the edit changed the answer, behavior, or presentation. |
| **8. Validate and report for the paper** | Reproduce `main_v1` first using the plan’s appendix. Test the selection logic with ties, inapplicable operators, identical outputs, missing controls, and incomplete model panels. Then lock the category recommendations and test fresh prompts using the held-out protocol in Section 4. Report coverage, paired gaps and uncertainty, and unresolved winners. | Retrospective numbers reproduce, and each paper claim matches its evidence status. |

## Repository entry points and outputs

- Reuse the operator registry and candidate-building logic in the study runner. Use a separate study ID for new runs and supply an explicit allowlist for validation prompts when implementing the new entry point. [Study runner](../../experiments/run_study.py)
- Reuse the scored pairs and control matching in the study analysis. Prepare discovery results from the existing `analysis_pairs.csv`, `candidates.jsonl`, and `study_manifest.json` before scheduling new model calls. [Study analysis](../../experiments/analyze_study.py) · [Main study inputs](../../results/study/main_v1/)
- Write `analysis/category_operator_rankings.csv` for the category recommendations and `analysis/prompt_operator_maxima.csv` for traceable prompt results. A per-prompt report should include the exact edit, smallest-edit result when applicable, and the IDs needed to locate full responses.
